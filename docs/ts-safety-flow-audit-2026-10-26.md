## ขอบเขตและผล

| Flow | สิ่งที่ตรวจ | ผล |
| --- | --- | --- |
| Ticket | CS รับงาน → ส่งต่อ → คิว T&S ที่ยังไม่มีคนรับ → takeover → งานของฉัน; CS ยังตอบแชต; ปิดงาน/ประวัติ; version และสิทธิ์ moderation | ผ่านเทสต์ API/ฐานข้อมูลและ unit tests |
| Dispute | CS รับงาน → ส่งต่อพร้อม memo → T&S รับงาน → ส่งกลับ CS พร้อม checklist → CS บันทึกผล → ส่งกลับ T&S → ตัดสิน → ประวัติ | ผ่านเทสต์ API/ฐานข้อมูล รวมตรวจรายการและยอดรวมของคิวแต่ละช่วง |
| Dispute ที่มีการทำงานพร้อมกัน | แย่งรับงาน, โอนงานชนการตัดสิน, การพักเงินชนการตัดสิน/ชำระเงิน, คืนเงินแล้วห้ามคืนสถานะผิด, สิทธิ์แชตแยกผู้ซื้อ/ผู้ขาย | ผ่านเทสต์ฐานข้อมูลและสิทธิ์ API |
| Report | แยกประเภทบัญชี/สินค้า/รีวิว, unassigned/mine/history, รับงานก่อนตัดสิน, ห้ามตัดสินงานคนอื่น, บันทึกเหตุผล/ผู้ตัดสิน, ลบสินค้า/รีวิวและดำเนินการกับบัญชี | ผ่านเทสต์บริการ/ฐานข้อมูล; integration ของลบสินค้าใช้ HTTP server จำลองปลายทาง |
| หน้า panel | filter, refresh, การเปิดรายละเอียดล่าสุด, เปลี่ยนเคสระหว่างรอผล, สลับ transcript, เปิดหลักฐาน, ส่งคำตัดสินซ้ำเมื่อแชตขัดข้อง | ผ่าน frontend tests |

## จุดที่พบและแก้

1. คิว unassigned ของ T&S/Admin ไม่รวม ticket ที่ CS ส่งต่อและยังคง assignment เพื่อสนทนากับลูกค้า แก้ให้รวม ESCALATED ที่ assignee ยังตรงกับ chat responder และออกจากคิวเมื่อมีผู้รับช่วง
2. งานของฉันเมื่อเลือกทุกสถานะซ่อน ESCALATED ที่ T&S รับแล้ว แก้ตัวกรองสำหรับ T&S/Admin ให้คงงานส่งต่อที่รับไว้
3. ตัวเลือกสถานะ ticket ส่ง `WAITING_CUSTOMER` ซึ่ง backend ไม่รองรับ แก้เป็น `PENDING_USER`
4. คิวส่งต่อไม่ได้ refresh ตามช่วงเวลา/เมื่อกลับหน้าต่างเหมือน report ปรับให้ทุกแหล่งข้อมูล refresh
5. ผล action หรือการโหลดรายละเอียดเก่าอาจทับเคสใหม่ที่เลือก ป้องกันด้วยเลขรอบการเลือกเคส ทั้งก่อนและหลังโหลดรายละเอียด
6. report ใช้ข้อมูลจากตารางระหว่างรอรายละเอียดใหม่ ปรับให้รอรายละเอียดล่าสุดก่อนเปิดรับงาน และไม่ให้ผล claim เก่ากลับไปเปลี่ยนเคสที่เลือกใหม่
7. transcript หน้าก่อนหน้าของผู้ซื้ออาจแทรกเข้าฝั่งผู้ขายเมื่อเปลี่ยนแท็บระหว่างรอ ป้องกันผลจากรอบอ่านเดิม และแยก state ของ panel เมื่อเปลี่ยนข้อพิพาท
8. เมื่อตัดสินสำเร็จแต่ส่งผล/ปิดแชตไม่ครบ หน้าเดิมไม่มีทางลองใหม่หลังแสดง DECIDED เพิ่มปุ่มส่งผลเดิมซ้ำโดยคง reason/version/idempotency key เดิม ไม่ตัดสินใหม่

## ขอบเขตที่ยังต้องลองใช้งานจริง

ผลนี้ไม่ใช่การยืนยันทุกเส้นทางผ่าน browser หรือการส่ง notification ทุกชนิดระหว่างบริการจริง การทดสอบฐานข้อมูลแยกบริการมีการจำลอง Chat/Auth/Product บางจุด และมี log การส่ง notification ไปบริการที่ไม่ได้เปิดในบริบทเทสต์ การอ่านผ่าน gateway ยืนยันคิว/รายละเอียด/transcript จริง แต่ไม่ได้ทดลองตัดสินคืนเงิน ระงับบัญชี หรือลบสินค้าในข้อมูลใช้งานจริง

ควรลองผ่านหน้าเว็บ: CS ส่ง ticket ใหม่ให้ T&S, รับช่วงแล้วเลือกทุกสถานะ; ส่งข้อพิพาทพร้อม memo แล้วตีกลับพร้อม checklist; รับ report แล้วตัดสิน และตรวจผล/notification ฝั่งผู้ใช้ด้วยข้อมูลทดสอบที่ตั้งใจสร้าง
