# ผลแก้ flow CS กับ Trust and Safety — 27 ตุลาคม 2026

## 1. เกิน SLA อยู่ในคิว CS

- เปลี่ยนตัวตรวจ SLA ให้ทำเครื่องหมาย `breachedAt` และบันทึก `SLA_BREACH` โดยไม่เปลี่ยนสถานะ เจ้าของ CS ผู้ตอบแชต หรือ version ของ ticket
- รักษากำหนดเวลาเดิมไว้ การแสดงเกินกำหนดและการเรียงคิวตาม SLA จึงยังทำงาน
- ส่งต่อ T&S ผ่าน action ของเจ้าหน้าที่พร้อมเหตุผลตามเดิม
- การตรวจซ้ำไม่สร้างบันทึก breach ซ้ำสำหรับ target เดิม และเคส CLOSED/RESOLVED ไม่ถูกเปลี่ยน
- ยืนยันกับฐานทดสอบ: NEW ที่เกินกำหนดยังอยู่ใน unassigned ของ CS ไม่เข้าคิว ESCALATED ของ T&S; CS รับเป็น ASSIGNED แล้วตอบลูกค้าได้จริง และการเกินกำหนดภายหลังไม่ย้ายเจ้าของ

ไม่ได้ย้อนแก้สถานะของเคสเก่าที่ถูกส่งต่อก่อนเปลี่ยนนโยบายนี้ เพื่อรักษาการรับงานและการพิจารณาที่เจ้าหน้าที่ทำไปแล้ว

## 2. CS อ่านข้อพิพาทหลังตัดสินได้เฉพาะเคสที่เคยเกี่ยวข้อง

- เพิ่มสิทธิ์อ่านประวัติสำหรับ CS ที่เป็นเจ้าของ ผู้ส่งต่อ หรือมีประวัติเคยได้รับมอบหมายในเคสนั้น
- ใช้เงื่อนไขเดียวกันใน capabilities, API รายละเอียด/ค้นตาม order, การเปิดห้องแชต และ internal chat-access
- หน้า CS เปิดแชตของเคส DECIDED แบบ read-only ได้ แม้ผู้รับผิดชอบปัจจุบันเป็น T&S
- การส่งข้อความ แก้ไขหลักฐาน รับงานใหม่ ส่งต่อ เปลี่ยนเจ้าของ และตัดสินซ้ำยังถูกปิดตามเดิม
- CS ที่ไม่เกี่ยวข้องไม่สามารถอ่านรายละเอียดหรือแชตได้ รวมเคสเก่าที่ไม่มีเจ้าของปัจจุบัน เคส soft-deleted ยังคงข้อจำกัดเดิม

## 3. คิว CS อัปเดตเมื่อมีงานตีกลับ

- ดึงข้อมูลคิวและรายละเอียดที่เลือกเบื้องหลังตาม `dashboardRefreshMs` ปัจจุบัน 15 วินาที รวมเมื่อกลับ focus/กลับมาเห็นหน้าต่าง
- พักการรีเฟรชอัตโนมัติระหว่างอัปโหลดและระหว่าง mutation เพื่อไม่รบกวนงานที่กำลังทำ
- ไม่แสดง loading ของรายละเอียดเบื้องหลังจนแชตถูกถอดออก และไม่ล้าง capabilities เพียงเพราะการ refresh เบื้องหลังล้มเหลวชั่วคราว
- ใช้ generation ของ request กัน response เก่าทับเคสใหม่หรือผล action ที่เพิ่งทำสำเร็จ และกลับมารีเฟรชต่อได้แม้ action ล้มเหลวทันที
- ยกเลิก timer/listener เมื่อออกจากหน้า

## 4. รายละเอียด T&S ที่เปิดค้างอัปเดตตามงานที่ CS ส่งกลับ

- เพิ่ม polling/focus/visibility refresh ของรายละเอียดเคสเดิม ไม่ต้องปิดแล้วเปิด panel ใหม่
- พักระหว่างทำรายการหรือกรอก dialog ส่งคืน CS และป้องกัน response ก่อนรับงานมาทับผลรับงาน
- ไม่ให้ข้อมูล version เก่าย้อนทับ version ใหม่
- เก็บเหตุผลที่กำลังร่างไว้ หากมี version ใหม่ระหว่างเปิดยืนยันคำตัดสิน จะยกเลิกการยืนยันเดิมและให้ตรวจข้อมูลใหม่ก่อน
- แสดงปัญหาการ refresh แยกจากผลทำรายการและลองใหม่อัตโนมัติ
