## ข้อตกลงใหม่: แยก operational storage ออกจาก audit log

ผู้ใช้อนุมัติแบบใหม่ใน thread ปัจจุบันแล้ว โดยใช้ `shipping_address_snapshots` แยกจาก Shipping ตามข้อเสนอแรก ดู [ข้อตกลงล่าสุด](operational-storage.md) และ [หลักฐานการลงมือ](../evidence/operational-storage.md) ข้อตกลงใหม่นี้แทนแนวทางเก็บสถานะหลักใน log ของ Order/Product/Support ที่บันทึกด้านล่าง ส่วนบันทึกต้นทางยังเก็บไว้เป็นประวัติ ไม่ได้ลบหรือแก้คำอนุมัติย้อนหลัง

- [Auth implementation และผลตรวจ](../evidence/auth-service/implementation.md)

ผู้ใช้อนุมัติย้าย Auth `legacy_*` พร้อมข้อมูลไป `legacy_archive` แล้ว migration และการตรวจรักษาข้อมูล/constraints/indexes/sequence ผ่าน และอนุมัติ `reviews.product_id` เป็น logical reference เพื่อคงรีวิวและ ID หลังลบสินค้า ดู [หลักฐาน Auth](../evidence/auth-service/archive-implementation.md) และ work map สำหรับผลตรวจโดยผู้ช่วยหลัก

## ขอบเขตและกติกาที่ตกลง

1. M01 ขอเทียบ ER **ข้อ 1** กับ database/backend และตรวจว่าใช้ได้จริงไหม
2. M05 ขอแก้ให้ตรง design และ backend; M07 เลือกแนวทาง **ตรง ER ทุกตาราง/คอลัมน์** แต่ต้องรายงานความต่างครบก่อน ห้ามเดาหรือเปลี่ยนเอง
3. M14 อนุมัติแก้สะกดผิดและใช้ `created_at`, `reference_id`, `order_id`; M16 กำหนดชื่อ SQL เป็น `snake_case`
4. M16, M21, M27 ให้เสนอวิธีรักษาพฤติกรรม backend เพื่ออนุมัติก่อนลงมือ ไม่ตัดฟีเจอร์หรือซ่อนข้อมูลในคอลัมน์ผิดความหมาย
5. อนุญาตปรับ ER เพิ่มเฉพาะรายการที่ยืนยันแล้ว เช่น `product_categories`, `review_media` และ FK ใน Order ไม่ได้อนุญาตเพิ่มทุกอย่างโดยทั่วไป
6. ต้องย้ายและตรวจข้อมูลเดิมก่อนตัดคอลัมน์/ตาราง ไม่แต่งข้อมูลย้อนหลัง ไม่แตะข้อมูลจริงในการตรวจ

## ผลตรวจที่รายงานในบทสนทนาเดิม

- M04: `prisma validate` ผ่านทั้ง 4 service
- M04: ทดสอบจาก 115 ไฟล์ — ผ่าน 447, ข้าม 65, รายงานล้มเหลว 4; รายการล้มเหลวที่ตรวจพบติด PostgreSQL
- M04: DB โปรเจกต์ไม่รัน จึงยังไม่พิสูจน์ migration และ end-to-end กับ DB จริง และต้องระวัง migration Product/Order ที่ป้องกันการอัปเกรด DB เก่า
- M09–M11: ตรวจ 61 entity และจับคู่ attribute ใน draw.io หลังแก้การอ่านเส้นตามพิกัด
- `database/*.prisma` ทั้ง 3 ไฟล์เป็นสำเนาที่ต่างจาก schema backend; ER ระบุ type/nullability/default ไม่ครบ จึงรับรองความตรงในส่วนเหล่านั้นไม่ได้

ทั้งหมดนี้เป็น **ผลที่ผู้ช่วยรายงานใน thread เดิม** รอบบันทึกนี้ไม่ได้รัน tests, validate, migration หรือยืนยันฐานข้อมูลซ้ำ

## ข้อสังเกตที่ต้องใช้ฉบับแก้แล้ว

M09 เคยระบุว่า `Products.id` ไม่มีในแบบ แต่ M10 ถอนข้อสังเกตนี้: `Products.id`, `Marketing Audit Logs.id`, `orders.status` และฟิลด์แคมเปญหลายตัวมีใน ER จริง เส้น draw.io บางเส้นอ้างพิกัด ไม่ใช่ node ID จึงห้ามใช้ผลอ่านแบบก่อนแก้เป็นเหตุให้ลบหรือเพิ่มข้อมูล

## สถานะงานและขั้นต่อไป

- ใน thread ต้นทาง ผู้ช่วยระบุซ้ำว่ายังไม่ได้แก้ ER/schema/migration/backend หรือข้อมูลจริง ไม่มีหลักฐานในข้อความว่าดำเนินการแก้แล้ว
- รอบนี้ทำเฉพาะบันทึกและเก็บแหล่งอ้างอิง ไม่ได้ลงมือแก้ระบบ
- **อัปเดตจากบทสนทนาติดตาม:** ผู้ใช้อนุมัติย้าย 17 ฟิลด์เสริมของ `dispute_case` ไป `dispute_case_log` และเก็บ snapshot ที่อยู่ที่ลูกค้าเลือกใน `order_log.detail` แล้ว ยืนยันว่า evidence เชื่อม `dispute_evidence` ตาม ref เดิม; หลังคำอธิบาย ผู้ใช้ตอบ “ok” อนุมัติ rename `hold.source` → `hold_type` โดยคงข้อมูลและพฤติกรรมเดิมแล้ว ส่วนวิธีรักษา 2 ฟิลด์ role ใน log ยังต้องแจกแจง ข้อตกลงติดตามอยู่ในไฟล์ Order ไม่ได้แก้บทสนทนาต้นฉบับ M01–M46
- หลักฐาน/ตาราง `evidence`, mapping ของชื่ออื่น, event format, constraints และแผน migration ยังต้องแจกแจงตามแบบที่อนุมัติ ไม่ถือว่ารายละเอียดทุกตัวจบแล้ว
- หลังปิดรายการค้างจึงปรับ ER/schema/migration/callers ให้สอดคล้อง ตรวจบน DB ชั่วคราว รวม retry/restart, event ซ้ำ, concurrency, ข้อมูลย้อนหลัง, FK, คิว/SLA และสิทธิ์อ่านข้อความภายใน ผลเหล่านี้ยังเป็นแผน ไม่ใช่ผลผ่าน
