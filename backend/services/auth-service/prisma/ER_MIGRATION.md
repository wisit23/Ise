# Approved Auth ER keys and auto_messages

Canonical schema: `schema.prisma`. Amendment:
[`ER_AMENDMENT.md`](../../../../database/erdesign/Auth%20Service/ข้อ%201/ER_AMENDMENT.md).
Do not use `database/auth-service.prisma` as the deployment source.

## Migration contract

`20261014000000_approved_er_keys_and_auto_messages` is migration 8. It runs in an
explicit transaction, preserves all request-item rows and ID values, replaces
PK(id) with PK(requests_id, field_name), retains `id` as unique, then creates
`auto_messages` and its seller-profile FK/index. The prior composite unique index
already rejects duplicate request/field pairs; the replacement does not discard
or deduplicate data. Deployment must use the existing Auth migration path, not
`db push`, edited historical migrations, or manual history overrides.

The `auto_messages` columns are required. `is_active` defaults to false. UUIDs
for `message_id` and item `id` are generated by Prisma, not by PostgreSQL. Raw SQL
inserts must supply those IDs. Multiple messages per seller are supported. No
sending API/job/trigger is part of this task.

## Legacy archive migration

`20261014010000_archive_legacy_auth_tables` is migration 9. In one explicit
transaction it creates schema `legacy_archive` and runs
`ALTER TABLE public.<name> SET SCHEMA legacy_archive` for
`legacy_admin_operations_20261010`, `legacy_bulk_action_runs_20261010` and
`legacy_report_versions_20261010` (created by
`20261007125900_preserve_legacy_auth_data`) when they exist in `public`.
`SET SCHEMA` moves the same relation: no copy, rewrite or drop, so rows, OIDs,
constraints, indexes and owned sequences are preserved. A table absent from
`public` is skipped (fresh chains only have the bulk archive; an already-archived
table makes a repeat run a no-op). If `legacy_archive` already holds a table of
the same name while `public` still has it, the migration raises and the whole
transaction rolls back; nothing is merged or overwritten. Historical migrations
and `migrate.js` are unchanged. The archive tables are not ER entities and no
runtime code reads them. Retention/export of `legacy_archive` is still an open
policy decision; this migration only relocates.

## Disposable rehearsal

Requires the already-created disposable container
`ise-er-rehearsal-20261014` and an independent database **`auth_worker_er`** or **`auth_archive_er`** (for the
archive migration; create it once the same way).
Never point these commands at a development/production database. This rehearsal
**drops/recreates public in that database** between scenarios and leaves synthetic
legacy fixtures there at completion. It never operates on the parent's `auth_er`
database or stops/removes the shared rehearsal container.

From the repository root (POSIX shell example):

```bash
# Run once, only if this worker database does not exist.
docker exec ise-er-rehearsal-20261014 psql -U er_test -d postgres \
  -v ON_ERROR_STOP=1 -c 'CREATE DATABASE auth_worker_er'

# If generation is necessary, generate ONLY Auth. The client is shared in this
# checkout, so coordinate it with the parent; no other-service generation here.
DATABASE_URL=postgresql://er_test:er_test@localhost:55439/auth_worker_er \
  node node_modules/prisma/build/index.js generate \
  --schema backend/services/auth-service/prisma/schema.prisma

AUTH_ER_REHEARSAL=1 \
DATABASE_URL_AUTH=postgresql://er_test:er_test@localhost:55439/auth_worker_er \
  node --test backend/services/auth-service/test/approved-er.integration.test.js
```

Without `AUTH_ER_REHEARSAL=1`, the destructive rehearsal is skipped. With it,
the test requires localhost/127.0.0.1:55439 and exactly `/auth_worker_er` or `/auth_archive_er`, rejects
other databases/schemas, and overwrites child-process `DATABASE_URL` with the
validated test URL. It creates temporary copies of historical migrations in the
OS temp folder and removes them afterward; no repository migrations or `.env`
are rewritten. The test requires the Auth client to be available but does not
regenerate any client itself. SQL and Prisma both operate on the same named
worker database.

The six serial scenarios prove (1-4 below, then the two archive scenarios 5-6):

1. Fresh deployment of all 9 migrations; actual ER column sets for all 17
   tables; actual PostgreSQL PK, item-ID UK, FKs; HTTP seller submit/history,
   admin queue/approve/reject, role rejection, duplicate pending and stale
   snapshot rejection.
2. AutoMessage create/read/update/delete, Prisma and SQL inactive defaults,
   duplicate IDs, missing text, missing seller/buyer-only FK rejection, seller
   delete cascade; item composite-key CRUD, duplicate pair/ID and orphan
   rejection, parent delete cascade and transaction rollback after an earlier
   seller-profile write.
3. Populated 7-to-8 upgrade: the same HTTP consumer before/after, every existing
   row from the 16 runtime tables byte-for-byte as PostgreSQL row JSON, historical
   null snapshots and IDs unchanged. Injecting a conflicting `auto_messages`
   table makes migration 8 fail **after** the PK-switch statements; the prior PK,
   rows and indexes are restored by transaction rollback. Normal deployment then
   passes; redeploy is a no-op; reconnect can still read historical IDs.
4. No-history legacy baseline helper: direct shop fields become normalized items
   without losing IDs/timestamps/new values; decided rows retain unknown/null old
   values; KYC keys, role grants, password hash and archived admin/bulk/report
   metadata survive. A migrated pending request can be approved by the existing
   consumer and a second helper run is a no-op.

5. Archive: a populated 8-state database with all three legacy tables (serial
   column, extra index, CHECK) is upgraded. A forced conflict on the last table
   first rolls back every earlier move; then deploy succeeds. Row JSON, relation
   OIDs, constraints, indexes and sequence ownership are identical afterwards;
   `public` holds no `legacy_*`; the sequence continues; repeat deploy reports no
   pending migrations; the HTTP consumer works.
6. Archive: running the SQL twice is a no-op; a new same-name table in `public`
   is refused without touching the archive.

## Observed limits

After migration 9, `public` has exactly the 17 ER tables plus `_prisma_migrations`,
and a Prisma database-to-schema diff on a fresh install is empty. Prisma does not
model the `legacy_archive` schema; do not drop it to tidy the database.

The existing helper baselines a nonempty no-history database against five legacy
migrations, then deploys migrations 6-9 (the archive step included). This work preserves that behavior and tests a recognized legacy
fixture; it does not certify arbitrary unknown schemas as safe to baseline.
`admin_audits_actor_id_fkey`, `bulk_action_runs_actor_id_fkey` and
`executive_audit_logs_actor_id_fkey` are historically `NOT VALID`: they constrain
new writes but do not establish that every old row has a valid actor. No old
actors are fabricated or removed to validate them.

The draw.io is the inspected source. The PDF and stale Prisma copy are not
regenerated. Real-data upgrades, live deployment, browser interactions, and
cross-service paths are not covered. These checks use synthetic data only.
