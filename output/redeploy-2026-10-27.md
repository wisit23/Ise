## 1. รอบแรกทำอะไร และทำไมยังไม่เปลี่ยนโค้ด

รอบแรกผู้ช่วยใช้ `kubectl rollout restart` กับแอปทั้ง 7 ตัว ซึ่งสร้าง pods ใหม่จาก image เดิม ไม่ได้ build โค้ดใหม่ การรายงานตอนนั้นว่า redeploy เสร็จจึงไม่ตรงกับผลลัพธ์ที่ผู้ใช้ต้องการ

```bash
sudo k3s kubectl -n reloop-production rollout restart \
  deployment/auth-service deployment/product-service \
  deployment/order-service deployment/chat-service \
  deployment/support-service deployment/gateway deployment/frontend
```

รอบนั้น rollout ผ่านและตรวจ HTTP ได้ แต่ยังใช้ image tag `run-20261026t065310z-3363042` จึงใช้เป็นหลักฐานว่าอัปเดตโค้ดไม่ได้ การที่ checkout บน server อยู่ commit ล่าสุด ก็ไม่ได้พิสูจน์ว่า image ที่รันอยู่ถูก build จาก commit นั้น

ผู้ใช้จึงยืนยันให้ build/deploy ตาม main บน GitHub โดยไม่รวมงานที่ยังไม่ได้ commit ในเครื่อง Windows และอนุญาตให้กด Connect เมื่อ Web SSH หลุด

## 2. ช่องทางที่ใช้

ใช้ SSH Terminal ผ่านเว็บ `https://init-d.cskmitl.com/status` ไม่ได้ SSH จาก PowerShell ในเครื่อง Windows คำสั่ง build/deploy ทำงานบน server ด้วย root ผ่าน sudo และอยู่ใน tmux เพื่อให้ทำงานต่อได้เมื่อ Web SSH หลุด

ระหว่างงานมี session หลุดและเครื่องมือควบคุมเว็บอ่าน screenshot หมดเวลา จึงใช้ช่องทางควบคุม Chrome และกลับมาอ่าน DOM ของ terminal แทน มีจังหวะที่ผู้ช่วยส่ง Enter โดยยังไม่มีช่อง terminal พร้อมใช้งาน ทำให้หน้าต่างปิดและต้องเชื่อมต่อใหม่ เหตุการณ์นี้ไม่ได้เปลี่ยนข้อมูลแอปหรือเริ่ม build ก่อนพร้อม

## 3. จัดการไฟล์ค้างบน server

ก่อน deploy พบ:

- `docker-compose.prod.yml` มีการเพิ่ม build argument `NEXT_PUBLIC_API_URL`
- `.codex-backup-prod-start/`
- `.codex-backup-same-origin/`
- `deploy/production-cloud/__pycache__/`
- `docker-compose.override.yml` เดิม ซึ่งกำหนด restart policies
- `docker-compose.yml.bak-before-init`

สคริปต์กำหนดให้ checkout สะอาดก่อน fetch/fast-forward main จึงจัดการดังนี้:

1. เก็บ tracked diff เป็น `tracked.patch` และคัดลอก `docker-compose.prod.yml` เดิมไว้
2. ย้ายไฟล์และโฟลเดอร์ untracked ที่ระบุข้างต้นออกจาก checkout ไปยังที่สำรอง
3. คืน `docker-compose.prod.yml` ให้ตรง HEAD ด้วย `git restore --source=HEAD -- docker-compose.prod.yml`

สำเนาเดิมอยู่บน server ที่:

```text
/var/lib/reloop-deploy-k8s/source-backup-20261027T110204Z/
```

ไม่ได้เขียนทับ `.env` ไม่ได้เปลี่ยนรหัสผ่าน และไม่ได้รวมงานค้างจากเครื่อง Windows ไป deploy

## 4. Preflight หยุดเพราะ build configuration

การรันสคริปต์ครั้งแรกหยุดด้วย:

```text
Frontend build NEXT_PUBLIC_API_URL must match its runtime environment.
```

สาเหตุคือ config runtime ของ server มี API URL แต่ production Compose ใน main ไม่ได้ส่ง build argument ที่ validator ต้องการ จึงสร้าง config เฉพาะ server ใน `/root/Ise/docker-compose.override.yml` ดังนี้:

```json
{"services":{"frontend":{"build":{"args":{"NEXT_PUBLIC_API_URL":"${NEXT_PUBLIC_API_URL}"}}}}}
```

เพิ่ม `/docker-compose.override.yml` ใน `.git/info/exclude` เพื่อให้ config เฉพาะเครื่องอยู่นอกชุด source ที่ Git ติดตาม ไม่มีการแก้ `.gitignore` ใน repository หรือเปลี่ยนโค้ดแอป/สคริปต์บน main ค่า API URL มาจาก `.env` เดิมของ server

## 5. Build หยุดรอ Prisma engine

หลังผ่าน preflight การ build ค้างที่ npm postinstall ของ Prisma:

- npm registry ติดต่อได้ HTTP 200
- URL ดาวน์โหลด Prisma engine ที่ต้องใช้หมดเวลาหลัง 20 วินาที โดยไม่ได้รับข้อมูล
- engine version ที่ตรวจพบ: `605197351a3c8bdd595af2d2a9bc3025bca48ea2` (Prisma 5.22.0)

จึงดึงเฉพาะ `/root/.cache/prisma` จาก Docker images รุ่นเดิมมาไว้ที่:

```text
/var/lib/reloop-deploy-k8s/build-cache/prisma/
```

เริ่มจาก Auth แล้วพบว่า Product ต้องใช้ target Windows เพิ่มตาม schema บน main จึงรวม cache จาก Product, Order, Chat และ Support ด้วย ได้ cache ทั้ง `linux-musl-openssl-3.0.x` และ `windows` ของ engine version เดียวกัน

รูปแบบคำสั่งที่ใช้ดึง cache:

```bash
cid=$(docker create docker.io/reloop-production/<service>:run-20261026t065310z-3363042)
docker cp "$cid:/root/.cache/prisma/." <private-cache-directory>
docker rm "$cid"
```

container ที่สร้างเพื่อคัดลอก cache ไม่ได้ถูก start และถูกลบเมื่อคัดลอกเสร็จ หยุดเฉพาะ build ที่ค้างด้วย `tmux send-keys ... C-c` ก่อนเริ่มใหม่ แอปเดิมยังทำงานในช่วงนั้น

สคริปต์เดิมรองรับ engine cache ผ่าน named build context และสร้าง Dockerfile ชั่วคราวเอง จึงไม่ได้แก้ Dockerfile หรือ Prisma schema ของ repository และไม่ได้ใช้โค้ดแอปจาก image เก่ามาทดแทนโค้ด main

## 6. พื้นที่ disk ระหว่าง build/import

การเก็บ images ใหม่และเดิมทั้งใน Docker และ K3s ทำให้พื้นที่ว่างลดต่ำกว่าเกณฑ์ของสคริปต์ (อย่างน้อย 10 GiB ก่อนเข้าสู่ maintenance สำหรับรอบนี้)

การคืนพื้นที่ที่ทำ:

- ตรวจ metadata ของ build cache แล้วพยายามล้างตาม cache ID เฉพาะรายการที่ไม่ใช้งาน หลายรายการคืนพื้นที่ 0B; หนึ่งรายการคืนได้ 987.5 MB
- ล้าง cache เก่ากว่า 24 ชั่วโมงที่ description ตรงกับ npm/Prisma/app build คืนเพิ่มได้ 34.93 MB มีคำสั่ง filter ครั้งหนึ่งไม่ผ่าน parser ก่อนแก้ syntax; คำสั่งที่ parse ไม่ผ่านไม่ได้ล้างข้อมูล
- ตรวจว่า Docker มี container เพียง `reloop-tunnel` และตรวจว่า K3s ยังเก็บ image tag รุ่นเดิมครบ 10 รายการ
- ลบเฉพาะสำเนา Docker images ของแอป 7 ตัว tag `run-20261026t065310z-3363042` และ Auth image ของ build รอบที่ยกเลิก tag `run-20261027t111102z-524378`

คำสั่งลบสำเนา Docker images เดิม:

```bash
for app in auth-service product-service order-service support-service chat-service gateway frontend; do
  docker image rm "docker.io/reloop-production/$app:run-20261026t065310z-3363042"
done
docker image rm docker.io/reloop-production/auth-service:run-20261027t111102z-524378
```

ไม่ได้ลบ images ใน K3s, database images, volumes, ฐานข้อมูล หรือไฟล์อัปโหลด และไม่ได้ใช้ system/volume prune หลังคืนพื้นที่เหลือประมาณ 11 GiB จึงผ่าน guard ของสคริปต์ พื้นที่ว่างตอนตรวจสุดท้ายคือ 10.35 GiB

## 8. ผลตรวจหลัง deploy

ตรวจจาก Kubernetes API และ journal:

- Deployment ทั้ง 10 ตัวมี readyReplicas=1 และ updatedReplicas=1
- Image ของ deployments ตรงกับ journal
- แอปทั้ง 7 ตัวใช้ `docker.io/reloop-production/<service>:run-20261027t111615z-529952`
- Journal status เป็น `ready`
- Server HEAD ตรงกับ GitHub main จาก `git ls-remote` อีกครั้ง
- `git diff HEAD` มีขนาด 0 bytes

ตรวจ HTTPS ผ่าน public origin:

| สิ่งที่ตรวจ | ผล |
| --- | --- |
| `/` | HTTP 200 |
| `/api/products/feed?limit=1` | HTTP 200 และ JSON มี items เป็น array |
| `/api/chat/socket.io/?EIO=4&transport=polling` | HTTP 200 และ Engine.IO handshake มี sid |
| Public WebSocket upgrade | HTTP 400, Server: nginx, `{"code":3,"message":"Bad request"}` |
| WebSocket ผ่าน gateway host port บน server โดยตรง | HTTP 101 Switching Protocols |

ข้อจำกัดที่ยังอยู่: WebSocket ผ่านโดเมนสาธารณะยังไม่ผ่าน แต่ gateway ภายใน upgrade ได้ ผลนี้ชี้ว่าต้องตรวจเส้นทาง proxy ระหว่างโดเมนกับ gateway เพิ่ม ยังไม่ได้พิสูจน์ว่า proxy ตัวใดเป็นต้นเหตุ และไม่ได้แก้ proxy/nginx/tunnel ในงานนี้ Chat polling ผ่าน ไม่ได้ทดสอบการส่งข้อความจริงระหว่างผู้ใช้

ไม่ได้ทดสอบ user flows ครบทุกอย่าง เช่น login, order, upload หรือ email และไม่ได้อ้างว่าตรวจข้อมูลทุกแถวก่อน/หลังแล้ว การรักษาข้อมูลอาศัย deployment แบบเดิมที่ใช้ persistent storage และไม่ได้สั่ง reset/migrate ข้อมูล

## 9. สิ่งที่คงไว้สำหรับรอบถัดไป

- เก็บ backup ของ config ค้างเดิมไว้ใน path ที่ระบุ

- เก็บ engine cache ที่สคริปต์รองรับ เพื่อลดการดาวน์โหลดซ้ำ
